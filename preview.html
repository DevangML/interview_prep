Prerequisite

Dart you actually need

Not “learn all of Dart”. Learn these patterns.

Goal: be able to read Flutter code without stopping at the language itself.

1. Variables + null safety

final = assign once. ? = may be null. ! = “I know it isn't null.”

final String name = 'Dev';
String? nickname;

print(nickname ?? name);

2. Functions + callbacks

A function can be stored and passed around. This is the engine behind callbacks like onPressed.

void save() {}
ElevatedButton(
  onPressed: save,
  child: const Text('Save'),
);

3. Classes + constructors

Widgets are mostly classes whose constructor arguments describe configuration.

class User {
  final String name;
  User(this.name);
}

final u = User('Sam');

4. Collections

Flutter UI is frequently “data → map → widgets”.

final names = ['A', 'B', 'C'];

Column(
  children: names
    .map((n) => Text(n))
    .toList(),
);

5. async / await

UI often asks for data that arrives later. Future<T> means “a T later”.

Future<String> load() async {
  return await api.fetchName();
}

6. Immutability intuition

Flutter likes replacing descriptions rather than mutating UI objects directly. Learn final, constructors, and “new value = old value + change”.

final next = List.of(old);
next.add('new');
Dart shortcut: don't memorize syntax first. Recognize these six patterns and then let the Flutter examples teach the rest.
01 · Architecture

The layers

Pattern
Higher layers describe; lower layers execute.

Flutter is layered. Your normal work happens in the Dart framework; underneath are dart:ui, the engine, then the platform embedder.

Your app → Flutter framework → dart:ui → engine → embedder → OS
Don't memorize every class. Remember the direction of responsibility.
Why Flutter feels cross-platform
Flutter owns most of the pixels.

Instead of translating your widgets into the OS's native widget toolkit, Flutter builds, lays out, composes and paints its UI itself. The platform still supplies services and lifecycle plumbing.

Flutter UI ≠ “Android TextView / iOS UILabel underneath”
Flutter UI = Flutter's own rendering model
Trade-off: native controls don't automatically exist inside Flutter's scene; native views need special integration.
02 · Architecture

Anatomy of a Flutter app

Pattern
App, framework, engine, embedder, runner = responsibilities.

Dart app: your business logic + UI composition. Framework: high-level Flutter API. Engine: low-level runtime and rasterization. Embedder: OS glue. Runner: platform app package that wires it together.

main.dart
  ↓
Flutter framework
  ↓
Flutter engine
  ↓
Android Activity / iOS ViewController / desktop host
  ↓
installed app
Pattern
Know boundaries, not source-code internals.

For everyday Flutter work, ask “Which layer owns this problem?” before diving deeper.

Usually your problem

Widgets, state, layout, navigation, app logic, packages.

Usually framework / engine territory

Render pipeline, rasterization, embedder startup, platform lifecycle.

03 · Core pattern

Reactive user interfaces

The sentence that unlocks Flutter
Pattern
UI = f(state)

You describe the UI for the current state. When state changes, Flutter rebuilds the relevant description.

Widget build(BuildContext context) {
  return Text('$count');
}

setState(() {
  count++;
});
Old mental model: “Find this UI object and change it.”
Flutter mental model: “Given the new state, what UI should exist?”
Pattern
Build is a description, not a place for side effects.

build() can run frequently. Keep it cheap and predictable. Fetching data, writing files or starting one-off side effects generally belongs elsewhere.

// Good mental split
state → build() → widgets

// Not ideal
build() → network request → mutate state
Quick check: When a counter becomes 2, what should your first thought be?
04 · UI building blocks

Widgets

Composition
Small widgets combine like LEGO.

Flutter intentionally uses one broad composition concept for layout, interactivity, themes, navigation and more.

Scaffold(
  appBar: AppBar(...),
  body: Center(
    child: Column(
      children: [...],
    ),
  ),
)
Building widgets
A widget is configuration.

Think of a widget as immutable instructions. The framework uses that configuration to create or update the underlying objects.

const Text(
  'Hello',
  style: TextStyle(fontSize: 20),
)
Widget state
Configuration can be replaced; persistent State can survive.

StatefulWidget separates the immutable widget configuration from a persistent State object that can change over time.

class Counter extends StatefulWidget {
  const Counter({super.key});
  @override
  State<Counter> createState() => _CounterState();
}
State management
Local state first; shared state only when sharing becomes real.

Pass data through constructors for simple trees. For shared descendants, patterns such as InheritedWidget (and packages built around it) avoid excessive “prop drilling”.

Theme.of(context)
Provider.of<T>(context)
Rule of thumb: don't start with a state-management package. Start with ownership: “who owns this state, and who needs it?”
05 · Rendering

Rendering and layout

Rendering model
Flutter builds a scene, then paints it.

Flutter's rendering pipeline is not “convert every widget to a native OS control”. Flutter's own rendering system calculates the scene that reaches the graphics layer.

widgets → elements → render objects
        → layout → paint → compositing → GPU
Input → GPU
An input event changes state; the next frame reflects it.

Touch, mouse and keyboard input enters through the platform/embedder, reaches Flutter, can change state, then a frame is produced when needed.

tap → callback → state change → rebuild/layout/paint → frame
Widget → Element
Widgets are replaceable descriptions; Elements provide continuity.

During build, Flutter matches new widget configurations against the existing element tree. This lets state and existing structure be reused when appropriate.

new Widget description
        ↓ match
existing Element position
        ↓
existing State / RenderObject may be reused
Layout
Constraints go down. Sizes go up.

This is the famous Flutter layout pattern. A parent gives a child min/max constraints. The child chooses a size within them and reports that size back.

Parent: “You may be 0–300px wide.”
Child:  “I choose 180px.”
Parent: places child at a position.
Debugging trick: when layout breaks, ask “What constraints did the parent give this child?”

06 · Platform

Platform embedding

Pattern
The embedder is Flutter’s host.

The platform-specific host initializes Flutter, connects lifecycle/input/window concerns, and provides the surface on which Flutter can render.

Android Activity
iOS UIViewController
desktop native host
        ↓
Flutter Engine
What varies by platform
Flutter UI is shared; hosting details are not.

Android, iOS and desktop have different lifecycle, input and windowing mechanisms. The embedder hides most of this from Dart application code.

Dart app logic
   ↓ stable Flutter API
platform-specific implementation
07 · Interoperability

Integrating with other code

Platform channels
Use messages when Dart needs a platform API.

Dart and Kotlin/Swift can exchange serialized messages through a named channel.

// Dart
const channel = MethodChannel('device');
final value = await channel.invokeMethod('getBattery');
FFI
Use FFI when you need a native C-compatible function.

dart:ffi binds Dart to native libraries. Unlike platform channels, the data does not need to cross a message serialization boundary in the same way.

typedef NativeFn = Int32 Function(Int32);
typedef DartFn = int Function(int);
FFI is powerful but lower-level. Learn it because you need native-library integration, not because Flutter requires it.
Native controls in Flutter
A native view is an island that Flutter must coordinate with.

Platform views such as AndroidView / UiKitView allow certain native controls to appear inside Flutter. This is useful for things such as complex maps or embedded browser content, but introduces synchronization/composition overhead.

Flutter scene
  ├─ Flutter widgets
  └─ native platform view
Hosting Flutter in a parent app
The relationship can be reversed.

Flutter can be embedded into an existing native application. The host app can load a Flutter engine and present Flutter content as one part of a larger native product.

Existing native app
       ↓
Flutter Engine
       ↓
Flutter screen / flow
08 · Web

Flutter web support

Pattern
On web, Dart becomes browser-executable output.

Flutter's framework is written in Dart, so web builds compile the framework and your application for the browser. Modern Flutter web builds can target JavaScript or WebAssembly.

Dart + Flutter framework
        ↓
JavaScript or WebAssembly
        ↓
browser
Important difference
Native Flutter has an engine/runtime stack; web has a browser-hosted path.

The C++ engine was designed around native operating systems. Flutter web therefore uses a browser-oriented compilation/runtime strategy rather than simply shipping that native engine unchanged.

native:
Dart → engine → OS

web:
Dart + framework → JS/Wasm → browser
09 · How to think

Further information without drowning

When you're stuck
Classify the bug before searching.

State bug? Who owns the state? Layout bug? What constraints arrived? Rebuild bug? Which dependency changed? Platform bug? Is Dart talking to native code? Performance bug? Which stage of build/layout/paint is expensive?

Deep internals
Only descend when the problem demands it.

The official docs point to deeper material such as Inside Flutter and rendering-pipeline talks. Treat those as “level 2 internals”, not prerequisites for building normal applications.

Level 1: widgets + state + constraints
Level 2: element/render trees
Level 3: engine / rasterization / embedder internals
