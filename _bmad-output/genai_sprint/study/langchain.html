Level 0 · the mental model

What LangChain actually is

If you remember one thing from this page, remember this — it prevents the most common wrong answer.

LangChain is plumbing. One interface across model providers, plus tools, structured output and integrations.

LangGraph is a state machine. You reach for it when the flow needs cycles, branching, or a human in the middle.

LlamaIndex is ingestion and indexing. Getting your documents into a retrievable shape.

They are layers, not competitors. Most candidates answer the comparison question as if you must pick one. That single mistake is what the question is testing for.

Level 1 · the four concepts

Models · Tools · Agents · Middleware

The current docs organise everything under these four. Be able to give one sentence on each without pausing.

🔌 Models

One interface for chat models and embeddings across providers. The point is portability — swap OpenAI for Bedrock without rewriting your app.

🔧 Tools

Functions the model can choose to call. You describe them; the model decides when. This is what turns a chatbot into something that acts.

🤖 Agents

Built on create_agent — a minimal, configurable harness. The model picks tools in a loop until it's done.

🛡️ Middleware

Cross-cutting concerns — guardrails, retries, routing, tool policies. This is the BFSI-relevant one.

Why middleware matters for your interview: in a bank, guardrails and tool policies aren't optional extras — they're the control layer an auditor asks about. Mentioning middleware unprompted signals you've thought past the happy path.
Level 2 · how it's built

create_agent, tool calling, structured output

The one abstraction

create_agent replaced the old zoo of agent types. If you learned LangChain from a 2023 tutorial you'll reach for initialize_agent and AgentExecutor — that's the stale answer.

Tool calling — the actual loop

user message │ ▼ model sees tool schemas ──► decides: answer, or call a tool? │ │ │ ▼ │ tool executes, result goes back in │ │ │◄───────────────────────────┘ (loop until done) ▼ final answer

The model never runs your code. It emits a structured request; your runtime executes it and passes the result back. Say that out loud — a lot of people describe it as if the model executes things itself.

Structured output

Binding a schema (usually Pydantic) so the model returns parseable objects rather than prose you regex. In production this is the difference between a demo and a system.

"Tool calling is the model choosing which function to invoke and with what arguments — but it doesn't execute anything. It returns a structured call, my runtime runs it, and the result goes back into the loop. Structured output is the same idea applied to the final answer: bind a schema so you get an object instead of prose."
Level 3 · the honest bits

LCEL, Runnables, and memory

LCEL — don't overclaim it

The pipe syntax (prompt | model | parser) composing Runnables, with batching, streaming and async for free. It's real and it's useful — but the ecosystem has moved toward create_agent for anything agentic. Know it, use it for linear chains, don't present it as the centre of LangChain in 2026.

Memory — the current story

The old ConversationBufferMemory classes are largely superseded. Persistence now lives in LangGraph: a checkpointer saves state per thread. If asked about memory, say where it actually lives now rather than reciting the deprecated classes.

The trap: answering LangChain from 2023 material. initialize_agent, AgentExecutor, ConversationBufferMemory — all signals that you learned this from an old course and haven't touched it since. One of these words costs you more than three right answers gain.
Level 4 · the near-certain question

LangChain vs LangGraph vs LlamaIndex

What it isReach for it when
LangChainGeneral framework — model interface, tools, structured output, integrationsLinear pipelines, RAG chains, tool calling
LangGraphGraph execution engine with persisted stateCycles, conditional routing, human-in-the-loop, parallel branches, resumability
LlamaIndexData ingestion, indexing, retrievalGetting documents in and queryable
"They're layers more than alternatives. LlamaIndex is strongest at getting data in and indexed. LangChain is the general framework — one model interface, tools, structured output. LangGraph is what you move to when the flow stops being linear and needs cycles, branching, or a human in the middle, because it gives you persisted state and resumability. In practice a real system often uses more than one."

Follow-up you should expect: "When would you NOT use LangGraph?" → A simple linear RAG chain. The state machine buys you nothing and costs you complexity. Being willing to say that is the seniority signal.

Level 4.5 · the one they'll actually ask

RAG in LangChain

RAG is 3/3 evidence. "How would you build this in LangChain?" is a live question — you need the shape, not memorised syntax.

The five pieces, in order

DocumentLoader → reads PDFs, HTML, DB rows into Documents TextSplitter → chunks them (RecursiveCharacterTextSplitter is the default) Embeddings → text → vectors (OpenAI, Bedrock, HuggingFace, local) VectorStore → stores + searches (FAISS, Chroma, pgvector, Pinecone) Retriever → the interface everything downstream talks to
The Retriever is the abstraction that matters. Anything that returns relevant documents for a query is a retriever — a vector store, a hybrid search, a database query, your own class. Downstream code doesn't care. That's what let you put an ACL filter inside yours without changing anything around it.

The chain shape — sketch this, don't memorise it

retriever = vectorstore.as_retriever(search_kwargs={"k": 5})

chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | model
    | StrOutputParser()
)

chain.invoke("what is the leave policy?")

Read it left to right: retrieve into context, pass the question through untouched, fill the prompt, call the model, parse to a string. If you can draw that, you can answer the question.

Integrations worth naming

PieceWhat you'd say
SplitterRecursiveCharacterTextSplitter is the sane default — it tries paragraph, then line, then word. Your project uses structure-aware chunking, which is the same instinct taken further.
Vector storeFAISS for local, Chroma for prototyping, pgvector when the org already runs Postgres, Pinecone/Weaviate managed. For BFSI the selection criterion is metadata filtering inside the search — that's your ACL point.
Retriever variantsMultiQueryRetriever, ParentDocumentRetriever (small-to-big), EnsembleRetriever (hybrid dense + BM25). Know the names and one line each.
Output parserStrOutputParser for prose, Pydantic parsers for structured. In production, structured almost always.
"In LangChain the piece that matters is the Retriever interface — anything that returns relevant documents for a query satisfies it, so the rest of the chain doesn't care what's behind it. That's exactly why I could put the access-control filter inside the retriever in my project without touching anything downstream. The chain itself is just retrieve into context, fill the prompt, call the model, parse the output."
If asked to write code: sketch the pipe chain above and say "roughly this — I'd check the current import paths, they've moved a few times." Nobody expects verbatim imports. Pretending to remember them exactly is a worse look than admitting they churn.
