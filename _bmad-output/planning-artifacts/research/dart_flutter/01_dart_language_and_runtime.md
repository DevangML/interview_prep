## A. Language surface

### A.1 Variables: final vs const, late, var/dynamic/Object?
- `final`: single-assignment, but the value can be computed at **runtime** (e.g. `final now = DateTime.now();`).
- `const`: value must be a **compile-time constant**; const objects are **canonicalized** (see A.11).
- `var`: static type is **inferred** at declaration and fixed thereafter (not dynamic — `var x = 1; x = "s";` is a compile error).
- `dynamic`: opts out of static type checking entirely for that variable — member accesses are deferred to runtime (`noSuchMethod` territory); a **top type**.
- `Object?`: also a top type (supertype of everything including `Null`), but **stays statically checked** — you must cast/promote before calling members. `dynamic` bypasses the checker; `Object?` doesn't.
- **Interview trap**: "isn't `dynamic` the same as `Object?`?" — No. `Object?` requires explicit casting to call type-specific members (compile error otherwise); `dynamic` allows any member access, deferred to runtime, and defeats some tooling/tree-shaking assumptions.
- **`late`**: escape hatch for definite-assignment analysis — declare a non-nullable var without initializing it immediately, promising it will be set before first read. Two use modes: (1) deferred init still checked eagerly at first access — throws `LateInitializationError` if read before assigned, or written to twice when combined with `late final`; (2) lazy init (`late final x = expensiveCall();`) — initializer runs only on first access, once. [dart.dev null-safety understanding](https://dart.dev/null-safety/understanding-null-safety)
- **Correct-answer kernel**: "`late` punches a controlled hole in the null-safety guarantee — trading a compile-time certainty for a runtime promise, verified by a runtime check (`LateInitializationError`) instead of the type checker."

### A.2 Sound null safety — full model
- Non-nullable by default: `String s` cannot hold `null`; must write `String? s` to allow null. Enforced **soundly** — the compiler can rely on the absence of `null` for `String` typed locations to safely omit runtime null checks, unlike TypeScript's unsound optional typing. [Sound null safety](https://dart.dev/null-safety)
- **Flow analysis / type promotion**: the analyzer tracks control flow within a function body — after `if (x != null) { ... }`, `x` is promoted to its non-nullable type inside that branch. This flow analysis is **local to functions**; it cannot promote a mutable field or a global/top-level variable because those can be mutated from anywhere (including other isolates' code running interleaved via getters) between the check and the use. [Flow analysis note](https://tsmakaay.hashnode.dev/dart-null-safety-flow-analysis-variables-and-keywords)
- **Definite assignment analysis**: guarantees a non-nullable local is assigned on every path before it's read — this is what `late` short-circuits.
- Operators: `!` (null assertion — throws at runtime if actually null), `?.` (null-aware member access, short-circuits to null), `??` (null-coalescing — returns left if non-null else right), `??=` (assign only if currently null).
- **Nullability and generics**: `T?` where `T` is a type parameter is subtly different from `T` bound to a nullable type — if `T` is instantiated with `int?`, then plain `T` is already nullable; `T?` in that case is still just `int?` (no double-nullable types in Dart — nullability doesn't stack).
- **Interview trap #1**: "does `!` make it null-safe?" — No, it's an assertion that *disables* the safety net for that expression; a wrong assumption throws `TypeError`/`Null check operator used on a null value` at runtime. It's the equivalent of Kotlin's `!!`.
- **Interview trap #2**: "why can't Dart promote a nullable field the same way it promotes a local?" — Because a field can be mutated by any concurrently-visible reference (getters, other methods) between the null-check and use; Dart's flow analysis is intentionally scoped to what it can prove for a single function's local control flow. Workaround: copy the field to a local first.
- **Correct-answer kernel**: "Non-nullable types are the default; nullability is opt-in via `?`; the compiler proves absence of null through flow analysis + definite assignment, and `late`/`!` are the two explicit places you trade compile-time proof for a runtime promise."

### A.3 Type system: soundness, variance, bounds, top/bottom types
- **Soundness**: Dart 2+ has a *sound* type system — if it type-checks, the types are guaranteed to hold at runtime (mod explicit unsound escape hatches like `dynamic`, unchecked casts, and unsound covariant generics before opting into checks). [Sound problems guide](https://dart.dev/guides/language/sound-problems)
- **Generic variance — Dart defaults to unsound covariance**: every type parameter is covariant by default: `C<T2>` is a subtype of `C<T1>` whenever `T2 <: T1` (e.g. `List<int>` is a `List<num>`). This rule is **not sound** — to preserve heap safety, the runtime inserts dynamic checks at the point of writing into a covariantly-typed collection; a program that type-checks can still throw a runtime `TypeError` if you go through a supertype-typed reference. [Kallen Tu, declaration-site variance](https://medium.com/dartlang/dart-declaration-site-variance-5c0e9c5f18a5)
  - Classic demo: `List<int> ints = [1,2,3]; List<num> nums = ints; nums.add(4.5); // runtime error — writing a double into what is really a List<int>`.
- **`covariant` keyword**: lets you *explicitly* override a parameter type in a subclass to a subtype (normally illegal — parameter types must be contravariant/invariant for override safety), and Dart inserts a runtime type check at the call site instead of a compile error. Example: `Animal.chase(Animal other)` overridden as `Cat.chase(covariant Cat other)`. [informal spec](https://dart.googlesource.com/sdk/+/61e97d010c98c27926b1a9d4f3d24c376adb91f5/docs/language/informal/covariant-from-class.md)
- **Declaration-site variance (`in`/`out`/`inout`)**: an experimental/added feature letting you annotate a class type parameter as `out T` (covariant, read-only positions), `in T` (contravariant, write-only positions), or `inout T` (invariant) — turns what would be a *runtime* type error into a *compile-time* error. [GitHub #753](https://github.com/dart-lang/language/issues/753) — **Confidence: Medium** on shipped/stable status as of 3.13; treat as an advanced/edge topic, not something a 3-YOE candidate must reproduce syntax for, but should be able to explain conceptually.
- **Bounded type parameters**: `class Stats<T extends num>` restricts `T` to `num` or subtypes; supports F-bounded polymorphism, `T extends Comparable<T>`. [dart.dev generics](https://dart.dev/language/generics)
- **Top types**: `Object?` (supertype of everything, statically checked) and `dynamic` (supertype of everything, statically *un*checked) are both top types but behave differently (see A.1).
- **Bottom type**: `Never` — the uninhabited type, subtype of *every* type. A function with return type `Never` never returns normally (always throws or loops forever) — useful for exhaustive-failure helpers. [Never type](https://dart.dev/language/built-in-types)
- **`FutureOr<T>`**: union-ish type meaning "either a `T` or a `Future<T>`" — used mainly for API flexibility (e.g. `then` callbacks that may or may not be async); Effective Dart explicitly advises *against* using `FutureOr<T>` as your own function's return type (it's meant for consuming flexible input, not producing flexible output).
- **Interview trap**: "is Dart's generics system sound?" — Trick question: the *default* covariant generics are famously the one deliberately unsound corner of an otherwise sound type system, chosen for ergonomics (arrays/lists behave the way Java's do), with runtime checks patching the hole.

### A.4 Classes: constructors, initializer lists, getters/setters, operators, `call()`, `noSuchMethod`
- **Constructor kinds**: generative (default, allocates+initializes), named (`Point.origin()`), factory (doesn't necessarily create a new instance — can return a cached/subtype instance; cannot access `this` before returning), redirecting (`Point.origin() : this(0,0);` — forwards entirely to another constructor of the same class, no body allowed), const (all fields must be final, all arg expressions const — enables canonicalization).
- **Initializer list**: runs *before* the constructor body, before `super(...)`'s target executes conceptually the list order is: initializer-list expressions (left to right) → superclass constructor call → constructor body. Used for `assert()`s and const-safe field initialization that can't be a simple default value.
- **Super parameters (Dart 2.17+)**: `Vector3d(super.x, super.y, this.z);` forwards straight to the super constructor's corresponding parameter, eliminating repetitive `: super(x, y)` boilerplate. Constraint: if the super call has positional args already, you can't *also* forward positionally. [Dart 2.17 blog](https://dart.dev/blog/dart-2-17-productivity-and-integration)
- **Primary constructors (stable in 3.13)**: `class Point(final int x, final int y);` declares fields *and* the constructor in the class header — eliminates the field-declaration + parameter + assignment triplication. New lints (`use_declaring_parameters`, `initialize_in_field_declaration`) push migration. [3.13 blog](https://dart.dev/blog/announcing-dart-3-13)
- **Static vs instance**: static members belong to the class itself, not accessible via an instance reference, no implicit `this`.
- **Operator overloading**: `operator +(Point other) => Point(x+other.x, y+other.y);` — Dart allows overloading a fixed set of operators (`+ - * / ~/ % ~ & | ^ << >> >>> [] []= < > <= >= == unary-`), no arbitrary operator names, no overloading by different-arity for the same operator token.
- **`call()`**: implementing `call()` on a class makes instances **callable like functions**: `myInstance(args)` invokes `myInstance.call(args)`. Only one `call()` per class (no overloading by signature — Dart has no arity/type overloading at all, named/optional params fill that role). [Callable objects](https://dart.dev/language/callable-objects)
- **`noSuchMethod`**: override on `Object` to intercept invocations of members that don't statically/dynamically exist — receives an `Invocation` object. **Gotcha**: an object that implements `noSuchMethod` but *not* `call()` explicitly is **not treated as callable** — calling it with `()` is a compile error if the static type doesn't declare `call`, even though `noSuchMethod` could theoretically handle it; this was explicitly filed and closed as intended. [GitHub #37884](https://github.com/dart-lang/sdk/issues/37884), [noSuchMethod docs](https://api.dart.dev/dart-core/Object/noSuchMethod.html)

### A.5 Inheritance vs mixins vs interfaces — linearization order
- `extends` = single inheritance of implementation; `implements` = adopt a type's interface *without* inheriting its implementation (you must reimplement every member); `with` = mixin application; `on` = constrains what a mixin can be mixed into and is what `super` inside the mixin resolves against.
- **Mixin linearization**, precisely: `class C extends S with M1, M2, M3 {}` is defined by the language as sugar for a synthetic linear chain of anonymous classes:
  - `class S&M1 extends S implements M1 { <M1's members, possibly calling super which resolves to S> }`
  - `class S&M1&M2 extends S&M1 implements M2 { <M2's members, super resolves to S&M1, i.e. effectively M1/S> }`
  - `class S&M1&M2&M3 extends S&M1&M2 implements M3 { <M3's members, super resolves to S&M1&M2> }`
  - `class C extends S&M1&M2&M3 { ... }`
  - **Net effect**: the *last* mixin listed (`M3`) sits **closest to `C`** in the chain and its members **win** on plain member lookup (override anything earlier); but a mixin's own `super.foo()` call walks *backward* through the chain toward `S` (M3's super → M2, M2's super → M1, M1's super → S). This is why "later mixins override earlier ones, but each mixin's `super` call reaches the *previous* ones in the list, not `C`'s own overrides." Confirmed conceptually via [dart.dev mixins](https://dart.dev/language/mixins) (the `on` clause section) — the exact synthetic-class desugaring is standard Dart-language-spec knowledge, consistent across secondary sources, but **the official page fetched did not spell out the algorithm verbatim in the excerpt retrieved — Confidence: Medium-High** (matches long-standing Dart spec behavior, but re-verify against the language spec `class.md` if the interviewer pushes for spec-exact wording).
  - **Diamond resolution**: because the desugaring is a strictly linear chain (not a DAG), there's no classic diamond ambiguity — every mixin gets its own slot in the linear order, and conflicts are resolved purely by "closer to the end of the `with` list wins."
- **`mixin class`**: a Dart-3.0+ declaration usable as *both* a regular class (can be instantiated/extended) and a mixin (can be applied via `with`). Constraints: **no `extends` clause**, **no generative constructors declared** (only factory constructors allowed, since a class used as mixin can't have its own superclass-initializing constructor called through mixin application). [dart.dev mixins](https://dart.dev/language/mixins)
- **Breaking change in Dart 3.0**: plain classes can no longer be used as mixins implicitly — you must opt in with `mixin class` (previously, if a class had no unnamed constructor with args, you could just mixin it).
- **Interview trap**: "if M1 and M2 both define `greet()`, which wins with `with M1, M2`?" — **M2** (the *last* one listed wins), the opposite of what people assume from left-to-right reading intuition in some other languages. Also: "can a mixin have a constructor?" — no generative constructors, ever (mixins aren't instantiated on their own in the normal case).

### A.6 Dart 3 class modifiers: sealed, final, base, interface
- **`sealed`**: closes the hierarchy to the *same library* — all direct subtypes must be declared in that library. This is what enables the compiler to enumerate every possible subtype and give **exhaustiveness checking** on a `switch` over a sealed type with no `default` needed. Implicitly abstract (can't be instantiated directly). [Class modifiers](https://dart.dev/language/class-modifiers)
- **`final`**: closes the type for subtyping *outside the declaring library* — no `extends`, `implements`, or `with` from outside. "Final encompasses the effects of `base`."
- **`base`**: forces that any subclass (even outside the library) must itself continue to use `extends`/`with` — i.e. it prevents `implements` (interface adoption without inheriting behavior) from breaking an invariant the base class relies on, but still allows external subclassing via `extends`.
- **`interface`**: prevents `extends`/`with` outside the library — forces external code to use `implements` only, i.e. adopt the shape but write fresh implementations, so the author is free to change the internal implementation without breaking external subclasses (classic "program to an interface" enforcement). Can combine with `abstract` (`abstract interface class`) but **cannot combine** `interface` with `base`, `final`, or `sealed` — they occupy the same "modifier slot" (mutually exclusive access modifiers).
- **Rationale each modifier answers**: sealed = "I want to pattern-match exhaustively"; final = "don't touch my hierarchy at all from outside"; base = "you may extend me but not just fake my interface"; interface = "you may only implement my shape, not inherit my code."
- **Interview trap**: "what does `sealed` actually prevent that `abstract` doesn't?" — `abstract` only prevents *instantiation*; it says nothing about who can subclass or from where. `sealed` additionally confines all subtypes to the same library, which is the actual precondition for compiler-verified exhaustiveness.

### A.7 Records, patterns, exhaustiveness, if-case
- **Records**: anonymous, immutable, **structurally typed** aggregates — `(int, String) pair = (1, "a");` or named fields `({int x, int y}) p = (x: 1, y: 2);`. The *shape* (field count, types, and — for named fields only — names) determines the type; two unrelated libraries producing records of the same shape get the *same* record type with no declaration needed.
  - **Equality**: two records are `==` iff same shape and equal corresponding field values. Positional field *names* are documentation only and don't affect type/equality (`(int x,int y,int z)` and `(int r,int g,int b)` are the same type and can compare equal); named field *names* **do** affect shape/equality (`(x:1,y:2,z:3)` != `(r:1,g:2,b:3)`). [dart.dev records](https://dart.cn/language/records) — cross-checked, **Confidence: High**.
- **Patterns**: a new grammar category usable in variable declarations, `for`-loops, `switch` statements/expressions, and `if`-`case`. Includes destructuring (`var (a, b) = getCoords();`), object-pattern extraction of getters (`if (obj case Point(x: var px, y: var py))`), list/map patterns, and the shorthand `CheckingAccount(:var balance)` (binds `balance` straight from the matching getter).
- **Switch expressions**: `var result = switch (x) { 1 => 'one', _ => 'other' };` — expression form of switch, no fallthrough.
- **Exhaustiveness checking**: switch on a `sealed` (or `enum`, or `bool`) type is checked at compile time for full coverage — omit a case and it's a **compile-time error**, not a runtime crash on a future added subtype forgotten in one switch site. [Exhaustiveness spec](https://github.com/dart-lang/language/blob/main/accepted/3.0/patterns/exhaustiveness.md)
- **if-case**: `if (json case {'name': String name}) { ... }` — pattern match as a conditional, binding on success.
- **Correct-answer kernel**: "sealed classes + exhaustive switch is Dart's answer to algebraic data types / Kotlin `sealed class` + `when` — the compiler, not a runtime default branch, catches a forgotten case when someone adds a new subtype."

### A.8 Extension methods vs extension types
- **Extension methods**: `extension NumberParsing on String { int parseInt() => int.parse(this); }` — adds an instance method to *every* value whose **static type** matches, at zero cost after compilation (statically resolved), but the underlying object is untouched; can't hide members, can't create a new type.
- **Extension types (Dart 3.3+)**: a *new, compile-time-only type* that wraps an existing "representation type" and presents a **different, restricted interface**; the extension type's abstraction **disappears entirely at runtime** — there is no wrapper object allocated. An expression whose static type is the extension type is, at runtime, literally an instance of the representation type. [New in Dart 3.3](https://dart.dev/blog/new-in-dart-3-3-extension-types-javascript-interop-and-more), [Extension types](https://dart.dev/language/extension-types)
- **Key distinction from a wrapper class**: a hand-written wrapper class (`class Meters { final double value; Meters(this.value); }`) allocates a real heap object holding the wrapped value. An extension type `extension type Meters(double value) {}` compiles away completely — at runtime a `Meters` *is* a `double`, no allocation, no indirection. This is why extension types are the backbone of the new `dart:js_interop`/`package:web` static JS interop (wrap a JS object type with a safe Dart-side API, zero marshalling cost).
- **Interview trap**: "how is an extension type different from a wrapper class or from `typedef`?" — `typedef` is just an alias (no new type, no extra safety); a wrapper class gives you a real new nominal type but costs an allocation; an extension type gives you a real new *static* type (the compiler won't let you pass a raw `double` where `Meters` is expected) with **zero runtime cost** because it's erased.

### A.9 Enhanced enums, generics on enums
- Since Dart 2.17: enums can declare fields, methods, getters, operators, **const constructors** (constructor must be const; instance fields must be final), implement interfaces, apply mixins, and be generic. [Enhanced enums spec](https://github.com/dart-lang/language/blob/main/accepted/2.17/enhanced-enums/feature-specification.md)
- Still fundamentally a fixed, compiler-enumerated set of const instances (`values` list) — can't be subclassed or instantiated beyond the declared constants.
- **Trap**: candidates sometimes think enhanced enums make Dart enums equivalent to full classes — they're not: no additional instances can ever be created beyond the ones written in the enum body.

### A.10 Collections
- `List`/`Set`/`Map`/`Iterable` — `Iterable` is Dart's **lazy** sequence abstraction; most of its transform methods (`map`, `where`, etc.) build lazy wrappers that only compute on iteration, not eagerly (must materialize with `.toList()`/`.toSet()` to force it). [Iterable laziness — mentioned across dart:core docs]
- **Growable vs fixed-length lists**: `List.filled(3, 0)` is fixed-length by default (`growable: false`) — calling `.add()` throws `UnsupportedError`; `[1,2,3]` literal and `List.filled(n, v, growable: true)`/`List<int>.generate` are growable.
- **Spread / collection-if / collection-for**: `[...list1, if (cond) x, for (var i in items) i*2]` — compile-time collection-literal control flow, avoids building intermediate lists imperatively.
- **Custom iterators / `sync*`**: a `sync*` generator function returns a lazily-computed `Iterable` — each call to `.iterator.moveNext()` resumes the generator body up to the next `yield`; `yield*` delegates to another iterable/iterator. Mirrors `async*`/`Stream` but synchronous.
- **Interview trap**: "does `list.map(fn)` execute `fn` immediately for every element?" — No; it returns a **lazy** `Iterable` wrapper; `fn` runs per-element only as you iterate (or when you call `.toList()`), and multiple `.map()`/`.where()` calls chain without allocating intermediate lists — a common perf gotcha is people assuming `.map()` eagerly computes and calling it multiple times, redoing work each iteration since the lazy `Iterable` isn't cached.

### A.11 Const canonicalization
- The compiler **canonicalizes** const expressions: every `const Point(1,2)` in your source, no matter how many textual occurrences, resolves to the **same single object instance** at runtime (`identical(a, b) == true`), provided the const constructor call has structurally identical arguments. [Const tutorial](https://resocoder.com/2020/01/06/dart-const-tutorial-all-you-need-to-know-const-expressions-canonical-instances-and-more/)
- **Why this matters for Flutter**: Flutter's element/widget diffing uses `identical`/`==` checks; a `const Text('Hello')` subtree, being the exact same canonicalized instance across rebuilds, lets Flutter's framework **skip rebuilding that subtree entirely** — this is the actual mechanical reason "always use `const` constructors where possible" is a top Flutter perf tip, not just convention.
- **Interview trap**: "why does adding `const` in front of a widget actually make anything faster — isn't it just syntax?" — No: it changes runtime identity semantics. The framework's `canUpdate`/`didWidgetChange` machinery short-circuits on `identical()` for const widget instances.

### A.12 Error handling
- **`Exception` vs `Error`**: both implement nothing special beyond being throwable `Object`s (Dart lets you `throw` *any* object, not just Exception/Error subtypes, though convention says don't). `Exception` is the base for conditions a well-written program should anticipate and handle (I/O failures, format errors). `Error` (and subclasses `TypeError`, `RangeError`, `AssertionError`, `StateError`, etc.) represents **programmer bugs** — conditions that "should never happen" if the code were correct, and are not generally meant to be caught/recovered from in production logic. [Error handling](https://dart.dev/language/error-handling)
- **`throw` vs `rethrow`**: `throw` inside a `catch` block **creates a new stack trace** starting at that point (loses the original throw site); `rethrow` preserves the **original stack trace**, which matters for debugging/logging — a very common gotcha in production code that "fixes" an exception's context by accident.
- **`assert()`**: **stripped in release/production builds** (only active in debug mode) — never rely on it for real validation/error handling in shipped code; only for development-time invariant checking.
- **Interview trap**: "what happens if I `catch (e) { throw e; }` instead of `rethrow;`?" — Functionally similar exception propagates, but the stack trace attached now starts at the `throw e;` line, destroying the original failure location — a classic root-cause-debugging foot-gun.

### A.13 Closures, tear-offs
- Closures capture **variables by reference** (the variable binding, not a value snapshot) — so a closure sees later mutations to a captured variable. **Loop-variable capture bug that no longer exists**: older Dart versions shared one variable binding across all loop iterations for a `for (var i = 0; ...)` loop, so closures created inside captured the *same final* `i`; **Dart 3+ creates a fresh binding per iteration**, fixing the classic "all closures print the last index" bug automatically. [Loop closures discussion](https://medium.com/@nursbrat991229/understanding-closures-and-loop-behavior-in-dart-bc2ae719c232) — **Confidence: Medium** on exact version this changed (verify against `for`-loop variable capture spec if pressed on the exact version number; conceptually solid).
- **Tear-offs**: referencing a named function, method, or **named constructor** without invoking it (no parens) creates a closure with the same signature — `list.forEach(print);` tears off the top-level `print` function; `Point.new` tears off the unnamed constructor. Static/instance methods can be torn off (`obj.method` — captures the bound receiver).

### A.14 Metadata & code generation
- **Annotations** (`@override`, `@deprecated`, custom `@JsonKey(...)`) are just const-constructor-invoked metadata read by tools (analyzer, code generators) — the language runtime does nothing with most of them itself (except a couple the SDK special-cases like `@pragma`).
- **Code generation pipeline**: `build_runner` is the file-watching/build-orchestration package; `source_gen` layers on top, using `analyzer`'s AST to implement `GeneratorForAnnotation`, and emits `.g.dart` files wired in via `part` directives. `json_serializable` generates `fromJson`/`toJson`; `freezed` generates immutable data classes with `copyWith`, structural equality, and union/sealed-class-style variants. Typical multi-generator ordering: freezed → json_serializable → other generators (e.g. retrofit). [Code generation overview](https://medium.com/mj-studio/dart-code-generation-comprehensive-guide-490b15639c4e)
- **Interview trap**: "why not just use macros for this?" (see Section 0 — macros are cancelled; `build_runner` is not being replaced any time soon).

## B. Async and concurrency

### B.1 Event loop: microtask queue vs event queue
- Each isolate has **one thread** and one event loop with **two internal queues**: the **microtask queue** and the **event queue** (a.k.a. the "task"/event queue for timers, I/O, UI events). [Dart async blog](https://dart.dev/blog/dart-asynchronous-programming-isolates-and-event-loops)
- **Ordering rule (High confidence, consistent across every source checked)**: Synchronous code always runs first to completion → then the **entire microtask queue is drained completely** (including microtasks scheduled *by* other microtasks while draining) → **only then** does the loop pull **one** event off the event queue, process it (running any sync code + draining any newly-queued microtasks before moving on) → repeat. The microtask queue is fully drained between every single event-queue item — **event queue never gets a turn while microtasks are pending.**
- **`scheduleMicrotask(fn)`**: enqueues onto the microtask queue — runs before any pending Timer/IO callback, guaranteed FIFO among microtasks.
- **`Timer.run(fn)` / `Timer(duration, fn)`**: enqueues onto the **event queue** — always runs *after* the microtask queue is empty, and after other event-queue items ahead of it.
- **`Future.then()`/`await` callbacks schedule as microtasks** by default (not event-queue) — this is why chained `.then()` calls or `await`s appear to "cut in line" ahead of `Timer(Duration.zero, ...)` even though intuitively both look "immediate."
- **Starvation hazard, explicitly documented**: recursively scheduling microtasks (a microtask that itself schedules another microtask, forever) can **starve the event queue indefinitely** — a `Timer.run` callback registered after such a loop starts will *never* fire because the loop never finishes draining microtasks. [scheduleMicrotask docs](https://api.flutter.dev/flutter/dart-async/scheduleMicrotask.html)
- **Interview trap**: "if I do `Future(() => print('A')); scheduleMicrotask(() => print('B')); print('C');` what prints first?" — `C` (sync), then `B` (microtask beats even a same-"priority"-sounding `Future(...)`, because unadorned `Future(fn)` actually schedules via the event queue, not microtask — see next point), then `A`. **Gotcha most candidates get wrong**: `Future(fn)` (the default unnamed constructor) uses `Timer.run` under the hood (**event queue**), while `Future.microtask(fn)` explicitly uses the microtask queue — so `Future(...)` and `scheduleMicrotask(...)` are *not* equivalent priority.
- **Correct-answer kernel**: "microtasks always fully drain before the next macro/event-queue item runs; `await`/`.then()` continuations are microtasks; Timers and I/O callbacks are event-queue items — this two-tier design is functionally the same two-tier model as the JS event loop (microtasks/Promises vs macrotasks/setTimeout), which is the fastest way to explain it to an interviewer who knows JS."

### B.2 Future
- States: uncompleted → completed-with-value or completed-with-error (terminal, one-shot — a `Future` cannot "restart" or be reused, unlike a `Stream`).
- `then(onValue, {onError})`, `catchError`, `whenComplete` (finally-equivalent) — chain by returning either a value or another `Future` from `then`'s callback (auto-flattened, no `Future<Future<T>>`).
- Combinators: `Future.wait(list)` (all-or-nothing — completes when all complete, or with the **first** error unless `eagerError`/other options tune it), `Future.any(list)` (completes as soon as the *first* one completes, value or error), `Future.microtask(fn)`, `Future.sync(fn)` (runs `fn` synchronously if it doesn't throw/return a Future, still returns a `Future` wrapping the result — useful for uniform APIs), `Future.delayed(duration, fn)`, `Future.value(v)`, `Future.error(e)`.
- **Unhandled Future errors**: an error on a `Future` that is never `.catchError`'d/`await`ed-in-a-try-catch becomes an **unhandled async error**, reported to the current `Zone`'s error handler (crashes in debug; in Flutter, hits the global Zone/`FlutterError.onError` machinery) — a documented, "closed as intended" gotcha is that a `Future<List<Future>>` awaited via `Future.wait` where one inner future errors independently can throw "unhandled exception" surprises if not every branch is awaited/handled. [GitHub #47771](https://github.com/dart-lang/sdk/issues/47771) — best practice: always `await`, store-and-handle, or explicitly `unawaited()` a fire-and-forget Future.
- **Interview trap**: "if a Future in a list passed to `Future.wait` throws, what happens to the other futures?" — They keep running (Dart doesn't cancel Futures), but `Future.wait`'s own returned Future completes with the **first** error encountered (by default), silently dropping/needing separate handling for the rest unless you use `eagerError: false` and handle per-future.

### B.3 async/await desugaring
- An `async` function body is compiled into a **compiler-generated state machine** — conceptually a continuation-passing transform: local variables that must survive across an `await` point get hoisted into machine state; each `await` becomes a suspend/resume point where control returns to the event loop and resumes later via a callback registered on the awaited Future. Loops, `try`/`catch`/`finally`, and `break`/`continue` are all handled by the state machine so you can write ordinary imperative control flow. [State machine description](https://medium.com/@jiyadahammad74/asynchronous-dart-future-async-await-and-the-patterns-every-senior-flutter-dev-must-own-0e82132fe205) — **Confidence: Medium** on precise codegen mechanics (dart2js reportedly used an exception-based technique for some state transitions historically per SDK issue trackers; VM's native async support differs internally) — for interview purposes, "compiles to a state machine that suspends/resumes at each `await`, functionally equivalent to manually chaining `.then()` calls" is the correct-depth answer; don't over-claim exact bytecode shape without pointing at the actual CFE/kernel source.
- **Correct-answer kernel**: "`async`/`await` is syntactic sugar over `Future`/`.then()` chaining — the compiler builds a state machine so you can write it as straight-line code; it does **not** create a new thread, it's still cooperative scheduling on the single isolate event loop."

### B.4 Streams
- **Single-subscription** (default `Stream` — one listener ever, backpressure-friendly, models finite sequences like file reads/HTTP response bodies) vs **broadcast** (`StreamController.broadcast()` — multiple simultaneous listeners, models ongoing events like UI/WebSocket; a broadcast stream **drops events with no listeners**, doesn't buffer for late subscribers).
- `StreamController`: `add`/`addError`/`close` feed the stream; `onListen`/`onPause`/`onResume`/`onCancel` hooks fire on subscription lifecycle changes (never mid-event-delivery). [StreamController docs](https://api.flutter.dev/flutter/dart-async/StreamController/StreamController.html)
- `listen(onData, {onError, onDone, cancelOnError})` returns a `StreamSubscription` — call `.pause()`/`.resume()`/`.cancel()` on it for manual backpressure control.
- **Key gotcha, explicitly documented**: **broadcast streams do not propagate pause semantics to the underlying source** the way single-subscription streams do — pausing one broadcast listener doesn't stop event production for the others, so backpressure only meaningfully works with single-subscription streams. [GitHub #10201](https://github.com/dart-lang/sdk/issues/10201)
- `async*`/`yield`/`yield*`: an `async*` function body returns a `Stream` lazily — `yield value` emits one event and suspends until the consumer is ready for the next (naturally backpressure-aware for single-subscription streams — the generator won't run ahead of the listener); `yield*` delegates emission to another stream/iterable.
- `StreamTransformer`: wraps stream-to-stream transformation logic (what `.map`/`.where`/`.transform()` compose to) — lets you build a stream pipeline stage that itself manages a nested subscription and forwards pause/resume/cancel to the source.
- **Interview trap**: "can two widgets both `.listen()` on the same plain `Stream`?" — Only if it's a **broadcast** stream; a single-subscription stream throws `Bad state: Stream has already been listened to` on the second `.listen()` call — extremely common `StreamBuilder`/BLoC bug when a stream is accidentally single-subscription and shared across two consumers.

### B.5 Zones
- A **Zone** is an execution context/ambient environment that can intercept and customize behavior of code run "in" it — error handling, `print`, timer creation, microtask scheduling can all be zone-overridden.
- **`runZonedGuarded(body, onError)`**: runs `body` in a fresh child zone whose uncaught-error handler is `onError` — this is how Flutter/Dart apps catch **uncaught asynchronous errors** that would otherwise crash the isolate silently (since a normal `try`/`catch` around `runApp()` cannot catch errors thrown later, asynchronously, in a different microtask/event turn — by the time the error surfaces the original synchronous call stack is long gone).
- **Why Flutter specifically leans on zones**: it wraps the whole app's `main()`/`runApp()` execution in a zone so that any error thrown anywhere in any later-scheduled callback (timers, stream events, gesture callbacks) is still captured centrally rather than crashing with no top-level catcher — errors cannot cross zone boundaries, so this must be the *outermost* zone for it to catch everything.
- **Interview trap**: "why can't I just wrap `runApp()` in try/catch to catch all app errors?" — Because `try`/`catch` only catches synchronous exceptions unwinding the *current* call stack; async errors surface on a fresh stack in a future event-loop turn, long after the `try` block has already exited — that's precisely the gap `runZonedGuarded` closes.

### B.6 Isolates
- **Memory model**: isolates share **no memory** — each has its own heap; the *only* way to communicate is asynchronous message passing via `SendPort`/`ReceivePort`. This is Dart's actor-model-style answer to concurrency, deliberately avoiding shared-memory data races. [Concurrency in Dart](https://dart.dev/language/concurrency)
- **What can be sent** across a port: if sender/receiver share code (spawned via `Isolate.spawn`), the *transitive object graph* can be almost anything — primitives (`null`, bool, int, double, String), collections (`List`, `Map`, `Set` and their `LinkedHash*` variants) with sendable contents, and typed data. **Cannot** send objects holding native resources (e.g. subclasses of `NativeFieldWrapperClass1` — things wrapping a Dart:io Socket, an open File handle-like native resource, etc.) or closures capturing non-sendable state (in the general cross-isolate-group case; same-group same-code sharing is more permissive for some object kinds). [SendPort.send docs](https://api.flutter.dev/flutter/dart-isolate/SendPort/send.html)
- **`TransferableTypedData`**: a special wrapper that lets you **transfer ownership** of a large typed-data buffer to another isolate in **constant time** (no copy) — after transfer, the sending isolate's original reference can no longer be materialized; only the receiver can call `.materialize()` to get it back as a real typed-data view. Ideal for large binary payloads (images, byte buffers) where copying would be expensive. [TransferableTypedData docs](https://api.flutter.dev/flutter/dart-isolate/TransferableTypedData-class.html)
- **`Isolate.run(fn)`**: the modern, preferred high-level API — spawns an isolate, runs `fn` (a closure, not required to be a top-level/static function like the old `compute`), returns its result as a `Future`, and **cleans the isolate up automatically** when done. Preferred over `compute()` for new code since it's more expressive (handles closures) and doesn't require an extra Flutter dependency.
- **`compute(callback, message)`** (Flutter foundation helper): the simpler, older API — restricted to a **top-level or static function** plus a single argument (can't capture arbitrary closures over local state) — runs it on a spawned isolate and returns the result.
- **Isolate groups**: isolates spawned via `Isolate.spawn` from the same parent belong to the same **isolate group** and **share the same heap-adjacent resources** — program structure/JITed code, string/constant tables — even though each isolate still has its own mutable heap and cannot share *mutable* objects directly; this makes intra-group isolate spawning fast and memory-efficient (vs. spawning a fully separate process-like isolate group, which duplicates all of that). [Isolate groups](https://www.mintlify.com/dart-lang/sdk/concepts/isolates) — **Confidence: Medium-High** (well-established VM feature since ~Dart 2.15, but exact current default-on status/details worth re-checking against SDK source if grilled on internals).
- **When isolates beat async**: `async`/`await`/`Future` model **concurrency**, not **parallelism** — everything still runs on one thread/one CPU core, cooperatively yielding at `await` points; **CPU-bound work** (heavy JSON parsing of huge payloads, image processing, complex computation) will **block the event loop and freeze the UI** if done with plain async code on the main isolate, because there's no actual parallel execution happening. Isolates are Dart's only mechanism for true parallel execution across CPU cores; use them for CPU-bound work, not I/O-bound work (I/O-bound work is *already* handled efficiently by the single-threaded async model without an isolate, since I/O doesn't block the CPU).
- **Interview trap**: "does `await` make my HTTP call run on a separate thread?" — No. `await` only yields control back to the event loop while waiting; the underlying I/O is handled by the OS/event-notification mechanism, not by another Dart thread. Only `Isolate.spawn`/`Isolate.run`/`compute()` give you an actual separate execution context with its own thread.

### B.7 Comparisons interviewers like
- **Dart vs JavaScript event loop**: structurally near-identical two-tier model — Dart's microtask queue ≈ JS's microtask queue (Promise callbacks/`queueMicrotask`); Dart's event queue ≈ JS's macrotask/task queue (`setTimeout`, I/O callbacks). Both are single-threaded, cooperative, non-preemptive.
- **Dart vs Java threads**: Java's classic model pushes concurrency complexity into the runtime/OS via preemptive OS threads (or, more recently, virtual threads/fibers) — the programmer writes blocking-looking imperative code and the JVM schedules real parallel execution, with the tradeoff being classic shared-memory hazards (locks, race conditions, deadlocks). Dart/JS push the complexity onto the *programmer's control-flow structure* instead — single-threaded cooperative scheduling avoids data races **by construction** within one isolate, at the cost of requiring explicit async modeling (`Future`/`Stream`) rather than "just block a thread." Dart's isolates are the closest analogue to Java threads for true parallelism, but with **message-passing, not shared memory** — closer to Erlang/Actor-model processes than to Java `Thread`s.
- **Correct-answer kernel for this contrast**: "Dart avoids shared-memory concurrency bugs by never sharing memory between isolates at all (message-passing only), and avoids single-isolate races by being single-threaded and cooperative — Java gets parallelism-by-default with shared memory and needs explicit synchronization; Dart gets safety-by-default and needs explicit isolates when it actually wants parallelism."

## C. Runtime and compilation internals

### C.1 JIT vs AOT
- **Development (JIT)**: the Dart VM's JIT compiler compiles code just-in-time with **incremental recompilation**, enabling **hot reload** — peak developer velocity, full debugging support, slower/variable runtime performance, larger memory footprint from keeping the compiler+analysis machinery resident. [Compilers and snapshots](https://medium.com/@flutterdevs/compilers-and-snapshots-in-dart-3abdd1ee56e9)
- **Release (AOT)**: `dart compile`/Flutter release builds run the **AOT compiler** ahead of time to native machine code, producing a **precompiled runtime** image — a stripped VM with **no compiler component**, cannot load/interpret Dart source dynamically. Result: consistent performance, small/fast startup, no hot reload, no runtime `eval`-like capability, longer build times.
- **App-JIT snapshots**: an intermediate form introduced to cut JIT warm-up time for large long-running JIT tools (`dartanalyzer`, `dart2js`) — captures a "trained" snapshot from a representative run; the VM starting from it can still fall back to JIT-compiling further if live execution diverges from the training profile.
- **Hot reload mechanics, precisely**: on a source edit, the incremental (CFE) compiler recompiles **only the changed library/file** using its in-memory compilation state (throwing away just that file's stale state), producing a **delta kernel file**; `flutter_tools` ships this to the running VM, which **reloads the changed libraries from the new kernel** — critically, **no code re-executes** at reload time itself; the framework then triggers a widget rebuild, and *that* rebuild is what actually runs the new code paths. [Flutter Hot Reload blog](https://flutter.dev/blog/flutter-hot-reload)
- **What hot reload CANNOT do, and precisely why**:
  - **`main()` / top-level & static field initializers don't re-run** — they only execute once per process lifetime; hot reload reloads code definitions but doesn't replay the top-level execution that already happened. So changing `void main() { runApp(...) }` has no visible effect until restart.
  - **Changed class shape is rejected outright** by the VM's reload-safety checks: the VM rejects transitions **between regular classes, enums, and typedefs** (can't turn a class into an enum in place); rejects **changes to the number of type arguments** on a class (unsafe because of an internal "type argument prefix" optimization that assumes a stable shape); rejects **changes to the number of native fields** (native wrapper shape changes require corresponding native-code changes it can't hot-swap). [dart-lang/sdk Hot-reload notes, paraphrased via search — Confidence: Medium-High, could not fetch the exact wiki text verbatim in this session, cross-confirmed by the Flutter docs list below]
  - **App state IS preserved** across reload (this is the headline feature) — existing `State` objects, their fields, and the widget tree's runtime object graph survive; only the *code* backing them is swapped.
  - **`const` value changes**: per Flutter's official hot-reload docs, changing a `const` field's *value* is hot-reloadable and treated as if it's just an alias update, not a structural change — but changing whether something *is* `const` at all, or a `static`/global variable's initializer expression, is **not** re-run (same top-level-initializer rule as `main()`); the documented workaround is to convert a global to a `const` or a getter so it's recomputed. [Hot reload docs](https://docs.flutter.dev/tools/hot-reload) — **Confidence: Medium** on the const-specific nuance (this is a frequently-misremembered detail; the safe interview answer is "top-level/static initializers never re-run on hot reload, full stop — if in doubt, hot-restart").
  - **Generic type parameter count changes** (`class A<T>` → `class A<T,V>`), **enum↔class conversions**, and any **native platform code changes** (Kotlin/Swift/Java/Obj-C) all require a **full hot restart** (which does re-run `main()` and reinitializes all state, but is still faster than a full process/app reinstall).
- **Interview trap**: "does hot reload re-run `initState()`?" — No (a very commonly mis-stated "yes" answer) — `initState()` is a one-time widget-lifecycle call already executed; hot reload doesn't replay lifecycle callbacks, it swaps code and triggers a rebuild (`build()` re-runs, `initState()` does not). If you need `initState()` logic to pick up a code change, you need hot **restart**.

### C.2 Kernel, CFE, snapshots
- **Kernel / `.dill` files**: since Dart 2, all Dart tooling (VM, dart2js, DDC) shares one **front end**: the source is parsed and type-checked once into a common **Kernel AST**, serialized as a binary `.dill` file. This is what enables consistent semantics across VM/JIT/AOT/JS/Wasm backends. [Dart VM intro](https://mrale.ph/dartvm/)
- **CFE (Common Front End)**: the shared component (written in Dart itself) that does source → Kernel AST translation, used by every downstream compiler/backend.
- **Snapshot types**: (1) **kernel snapshot** — just the serialized Kernel AST, portable, still needs a VM to JIT/interpret it; (2) **JIT snapshot / app-JIT** — includes some already-compiled/"trained" code to cut warm-up; (3) **AOT snapshot** — fully compiled native machine code plus metadata, runs on the stripped precompiled runtime with **no** source-loading capability at all.

### C.3 Tree shaking
- The compiler performs **whole-program reachability analysis** starting from `main()` — anything (classes, functions, libraries) not transitively reachable from the entry point is **eliminated** from the final binary/JS bundle, commonly cited as a **30–50% size reduction** vs. an unshaken build. [Tree shaking overview](https://vibe-studio.ai/insights/tree-shaking-in-flutter-reducing-bundle-size-for-web-applications)
- **What defeats tree shaking**: `dart:mirrors` (full runtime reflection) — since the compiler operates under a **closed-world assumption** to determine what's reachable, unrestricted reflective access ("explore, modify, and dynamically invoke anything reachable transitively") makes it impossible to prove anything is unreachable, forcing the compiler to keep everything. Web/AOT toolchains **exclude `dart:mirrors` entirely** for this reason (a web build using it fails outright); the old workaround was a `@MirrorsUsed` annotation to scope what must be retained, but the modern answer is simply "mirrors aren't available outside the JIT/VM dev context — use code generation instead." [mrale.ph on mirrors](https://mrale.ph/blog/2017/01/08/the-fear-of-dart-mirrors.html), [tree-shaking + mirrors issue](https://github.com/dart-lang/sdk/issues/18217)
- Heavy `dynamic`-typed dispatch and unconstrained `noSuchMethod` usage similarly reduce how much the compiler can statically prove is reachable/unused, though they're less absolute blockers than mirrors.
- **Interview trap**: "why doesn't Dart have full reflection like Java?" — It does (`dart:mirrors`), but it's essentially **unusable for compiled/production targets** (web, AOT release) precisely because it's fundamentally incompatible with tree shaking and ahead-of-time whole-program optimization — which is why Dart's ecosystem leans on compile-time code generation (`build_runner`) instead of runtime reflection for things like JSON serialization.

### C.4 Dart VM object model & GC (sourced from official VM docs)
- **Tagged pointers**: object references use the low bit as a tag — **Smis** (small integers) have tag `0` and are **not heap-allocated at all**; the integer value is stored directly, shifted, in the pointer word itself (the VM stores twice the numeric value so the low bit is guaranteed 0) — meaning small-int arithmetic can often skip alloc/dealloc entirely. **Heap objects** get tag `1`; this costs nothing on access because the tag-removal is folded directly into the memory-offset math of load/store instructions. [Dart VM object model](https://mrale.ph/dartvm/types.html)
- **Double-word alignment trick**: heap objects are always allocated in double-word increments, with old-space objects at even boundaries and new-space objects offset by one word — letting the VM check an object's **generation (age)** with a cheap bit check instead of a boundary-address comparison.
- **Generational GC — two generations**:
  - **New space (young generation)**: collected by a **parallel, stop-the-world semispace scavenger** implementing **Cheney's algorithm** — live objects are copied from one semispace to the other; each parallel worker thread does **bump-pointer allocation** into its own local region of to-space (or promotes directly to old space if the object has survived enough scavenges), making allocation and copying extremely cheap. This generation is designed for **short-lived, high-churn objects** (classic example: ephemeral `StatelessWidget` instances rebuilt every frame). [Dart VM GC docs](https://mrale.ph/dartvm/gc.html), [chromium source mirror](https://chromium.googlesource.com/external/github.com/dart-lang/sdk/+/refs/tags/2.8.0-dev.14.0/runtime/docs/gc.md)
  - **Old space (mature generation)**: collected by **concurrent-mark-sweep** or **concurrent-mark-parallel-compact**. Marking traverses the live object graph, setting mark bits and pushing to a marking stack; sweeping then reclaims memory for anything left unmarked. The **sliding compactor** represents its forwarding table compactly by dividing the heap into blocks, recording each block's target address plus a per-block bit-vector of surviving double-words — this is how compaction avoids fragmentation over long app lifetimes without pausing for a full linear scan every time.
- **Allocation cost**: the common case (`AllocateObject`) is **bump-pointer allocation in new space** — essentially just incrementing a pointer, one of the cheapest possible allocation strategies, which is why Dart/Flutter code is written with an "allocate freely, especially short-lived objects" idiom (immutable widget rebuilds every frame is explicitly designed around this).
- **Why this design suits UI workloads**: UI frameworks like Flutter allocate huge numbers of small, short-lived objects every frame (widget instances, render objects, layout constraint objects) — the semispace scavenger handles this pattern near-optimally (cheap allocation, cheap collection of garbage that dies young), while the separate old-space collector independently reclaims long-lived state (App state, cached data) without needing to pause on every young-gen collection. This generational split is *the* standard justification interviewers expect: "most objects die young; separate the GC strategy by object lifetime and you get low pause times for the common case."
- **Confidence: High** — this section is drawn directly from the official Dart VM engineering docs (mrale.ph mirrors the canonical `runtime/docs/gc.md` from the SDK repo).

### C.5 dart2js / dart2wasm — web targets
- **dart2js**: compiles Dart to JavaScript; shares the same CFE front end. On this target, Dart's `int` type loses its native 64-bit two's-complement identity — JS numbers are IEEE-754 doubles, so integers are only exactly representable up to **53 bits of precision**; beyond that, distinct large integers can silently collapse to the same double value (`2^53` and `2^53 + 1` become indistinguishable) — this is a **precision-loss** failure mode, not a wraparound.
- **dart2wasm**: the newer Wasm compiler, shares the CFE front end, runs **type-flow analysis for tree-shaking**, maps Dart types onto native Wasm types, generates Wasm directly, and finishes with a Binaryen optimization pass. Because WebAssembly natively supports true 64-bit integers, **dart2wasm gives Dart's `int` its full native 64-bit two's-complement semantics on the web**, unlike dart2js — closing a long-standing semantic gap between "Dart on native" and "Dart on web." [WasmGC status](https://foresightmobile.com/blog/wasmgc-and-how-this-is-a-game-changer-for-dart-and-flutter)
- **Production status as of 2026**: WasmGC-based Flutter web shipped stable starting **Flutter 3.22 (May 2024)**; by 2026 it's described as "battle-tested and production-ready," with **over 58% of existing Flutter web apps compiling to Wasm with zero code changes**, ~2x average / 3x worst-case frame-rendering gains reported, and **~92%+ global browser coverage** for WasmGC (Chrome 119+, Firefox 120+, Edge 119+, Safari 18.2+) with an automatic JS-compiled fallback bundle for older browsers. Dart 3.13 adds **experimental Wasm deferred loading** (`--enable-deferred-loading`) for further initial-load-time improvements. [Try Flutter Web with WebAssembly](https://flutter.dev/blog/try-flutter-web-with-webassembly-week), [Dart 3.13 blog](https://dart.dev/blog/announcing-dart-3-13) — **Confidence: Medium-High** on the specific adoption percentages (marketing/blog-sourced numbers, not an SDK spec fact — treat the percentages as illustrative, not exam-precise).
- **Other web-target differences**: no true OS-thread isolates on the web (isolates on dart2js/dart2wasm are typically backed by Web Workers, a heavier-weight and more restricted primitive than native isolates); older `dart:html`/`package:js` interop don't compile to Wasm — modern code must use `package:web` + `dart:js_interop`.
- **Compile-mode semantic discrepancies**: at aggressive optimization levels (`-O3`/`-O4`), dart2js and dart2wasm diverge on unsafe-cast behavior — dart2js may print `null` on a bad cast under `-O4`, while dart2wasm **traps and crashes** the program — a known, currently-unresolved cross-target inconsistency for teams shipping both. [GitHub #56949](https://github.com/dart-lang/sdk/issues/56949)

### C.6 FFI
- **`dart:ffi`**: lets Dart call into native (C-ABI) shared libraries — define `Struct` subclasses mapping C struct layouts, `Pointer<T>` for native memory, `NativeFunction` typedefs for C function signatures, and `Pointer.fromFunction`/`NativeCallable` for passing Dart callbacks *into* native code.
- **`Finalizer` (dart:core) vs `NativeFinalizer` (dart:ffi)**: `Finalizer` runs a **Dart callback** when a Dart object becomes unreachable, but **makes no promise it will ever actually be called** (best-effort, GC-timing-dependent — never rely on it for critical cleanup). `NativeFinalizer` instead invokes a **native (non-Dart) callback function** and **does** guarantee it will be called at least once for every still-attached object before its isolate group shuts down (a stronger contract than the plain `Finalizer`) — but critically, the native callback must be able to run **outside a Dart isolate context**, so you cannot pass an FFI trampoline created via `Pointer.fromFunction` (that requires a live isolate) as a `NativeFinalizer` callback. [NativeFinalizer docs](https://api.flutter.dev/flutter/dart-ffi/NativeFinalizer/NativeFinalizer.html)
- **Native assets / build hooks** (stable direction since **Dart 3.10**): a `hook/build.dart` script in a package can compile or download native code (C/Rust libraries) as "Code Assets," automatically wired into `dart run`/`dart test`/`dart build`/`flutter run` — replacing ad hoc prebuild scripts for FFI packages needing bundled native binaries. [Hooks](https://dart.dev/tools/hooks), [dart-lang/native](https://github.com/dart-lang/native) — **Confidence: Medium** on exact stabilization milestone/version (multiple sources describe it as "available since Dart 3.10" but as of this research it may still carry an experimental/preview flag for some sub-features — verify `--enable-experiment` flag requirements if this comes up in depth).

### C.7 Numbers: int/double, overflow, `==` vs `identical`
- **Native (VM) `int`**: 64-bit two's-complement; arithmetic **wraps** on overflow (standard two's-complement wraparound, e.g. `9223372036854775807 + 1` wraps to the most-negative 64-bit value) rather than promoting to a bignum or throwing. [Numbers in Dart](https://dart.dev/resources/language/number-representation)
- **Web (dart2js) `int`**: represented as a JS double — safe/exact only up to `2^53`; beyond that, distinct integer values can **collapse into the same double** (precision loss, not wraparound) — the single most-cited native-vs-web numeric semantic gap. **dart2wasm closes this gap** by giving `int` true 64-bit semantics on the web too (see C.5).
- **`identical(a, b)`**: true iff `a` and `b` are **the exact same object reference** (or the same canonicalized primitive/const value) — this is what `Object`'s **default** `==` implementation delegates to, before any subclass overrides it.
- **Overriding `==`**: switches a class to **value equality** — but the language enforces (by convention, checked by lints, not the compiler itself) the **hashCode contract**: any two objects that are `==` **must** return the same `hashCode`, or they'll behave incorrectly (fail lookups, appear "duplicated") inside hash-based collections (`Set`, `HashMap`/the default `Map`) — override `==` and `hashCode` together, always. [Equality overview](https://apgapg.medium.com/demystifying-and-hashcode-in-dart-2f328d1ab1bc)
- **Interview trap**: "what's the difference between `==` and `identical()`, and when would they disagree?" — `identical()` is always reference/canonical-value identity, never overridable; `==` is overridable to mean "logically equal." Two distinct (non-const, non-canonicalized) objects with identical field values are `identical() == false` by default, but can be made `== true` by overriding the operator (e.g., a value-object `Point(1,2) == Point(1,2)` should be true even though they're different heap allocations) — and forgetting to override `hashCode` alongside `==` is the single most common bug here (objects silently "vanish" from a `Set` because lookups hash-bucket them incorrectly).

## D. Interview-shaped quick reference (misconception + kernel, by area)

| Area | What a 3-YOE candidate gets asked | Common misconception | One-line correct kernel |
|---|---|---|---|
| Null safety | "What does `late` actually do?" | "It just means nullable but lazy" | It's a promise to the compiler of definite assignment before first read, backed by a runtime check (`LateInitializationError`), not a type-level guarantee. |
| Null safety | "`!` vs `?.`" | "`!` is just a shorter `?.`" | `!` is an assertion that *removes* the safety net (throws if wrong); `?.` *preserves* it (short-circuits to null). |
| Generics | "Is Dart's type system sound?" | "Yes, fully" | Sound overall, but generics default to **unsound covariance** patched by runtime checks — the one deliberate hole. |
| Mixins | "M1, M2 both define foo() — which wins?" | "First one, left to right" | **Last** one in the `with` list wins (closest to the class in the linearized chain); each mixin's own `super` call walks back toward the earlier ones. |
| Class modifiers | "sealed vs abstract" | "Same thing" | `abstract` blocks instantiation only; `sealed` additionally confines all subtypes to one library, which is what makes exhaustive `switch` provable. |
| Extension types | "Isn't this just a wrapper class?" | "Yes, same cost, nicer syntax" | A wrapper class allocates a real object; an extension type is erased entirely at compile time — zero runtime allocation. |
| Event loop | "`Future(fn)` vs `scheduleMicrotask(fn)` — same priority?" | "Yes, both are 'async', should run similarly" | No — `Future(fn)` schedules via the **event queue** (`Timer.run`), `scheduleMicrotask` uses the **microtask queue**, which always fully drains first. |
| Async | "Does `await` give you a new thread?" | "Yes, it runs off the main thread" | No — single isolate, single thread; `await` only yields to the event loop, it doesn't parallelize. |
| Isolates | "When do I need an isolate vs just `async`?" | "Any slow operation" | Only for **CPU-bound** work that would otherwise block the event loop; I/O-bound work is already non-blocking under plain async. |
| Isolates | "Can isolates share objects?" | "Yes, if in the same isolate group" | No mutable object sharing ever — isolate groups only share immutable/code-level resources (JIT code, constants); communication is strictly message-passing. |
| Hot reload | "Does hot reload rerun `initState()`?" | "Yes" | No — lifecycle methods already executed aren't replayed; only `build()` reruns via the triggered rebuild. Structural/type-arg/enum-class changes force a full restart. |
| GC | "Why generational GC for Flutter?" | Vague "it's faster" | Most UI objects (widgets) die young; a cheap bump-allocated semispace scavenger handles that case near-optimally, while a separate old-gen collector handles long-lived state without adding pause time to every frame's garbage. |
| const | "Why does `const Text(...)` actually help performance?" | "Just avoids reparsing, minor thing" | It canonicalizes to one shared object instance — Flutter's diffing uses `identical()`, so the framework can literally skip rebuilding that subtree. |
| Numbers | "Does an int overflow the same on web and native?" | "Yes, same language, same behavior" | No — native wraps (64-bit two's complement); dart2js loses precision past 2^53 (JS double); dart2wasm restores true 64-bit semantics on web. |
| Metaprogramming | "When are Dart macros landing?" | "Should be stable by now, it's been years" | **Cancelled** (Jan 2025) — replaced in intent by narrower "augmentations" + continued reliance on `build_runner` codegen. |
| Records | "Are two records with same values but different field names equal?" | "Always equal if values match" | Only if the shape (including named-field names) matches — positional names are cosmetic, named-field names are part of the type. |
