        david_chisnall 2024-06-18 04:07:41

        C++ doesn’t have a stable ABI in the exact same way that C doesn’t: the ABI is not part of the language and is delegated to the implementation. Nothing in the C specification tells you how structures should be laid out (except that the first field must be at offset 0), how parameters are passed (in registers or on the stack), the assembly symbol name for C identifiers (some platforms prefix an underscore, some don’t), how static declarations are defined with symbol visibility, and so on.

        Most *NIX platforms converged on the System V ABI for C and its various psABI extensions. For *NIX, the system libraries and kernel are traditionally written in terms of C and so they define the types that they expose as C types and the system provides an ABI that, as an artefact of its implementation, has a trivial mapping to C. This means that there is no incentive to define a different C ABI, because you must also implement the platform’s one.

        This is not the case for other systems. Both classic Mac OS and Windows came from a time when Pascal and C both looked like they might be the long-term winner. MacOS used a lot of Pascal in the implementation and exposed Pascal types as the system interface, with C compilers aiming for compatibility. You can’t implement variadic functions with a Pascal calling convention (arguments are pushed left to right and so the top of the stack is the last argument and you need to know how many arguments there are to be able to find the first one) and so C compilers needed to implement a different calling convention for system-library calls. Windows was more language-agnostic and defined all of the system structures with types that were not native C types (but which could be represented with C, Pascal, or other-language types) and made the calling conventions explicit. C compilers for Windows picked the one that was the best fit for C as the default rather than inventing something new.

        For the last 20 or so years, pretty much every target that isn’t Windows has adopted the Itanium C++ ABI, which is defined in terms of C types (with the exception of two registers used for the exception ABI) and so can be mapped to any SysV psABI trivially. This has been stable and backwards compatible for longer than Rust has existed. You can compile a C++ compilation unit with any of gcc, clang, icc, xlc, and others and link it with another C++ compilation unit compiled with any version of one of the others (modulo bugs, which also affect C, such as LLVM’s failure to zero-extend arguments that are smaller than the word on x86-64 for a little while).

        Windows followed the same language-agnostic path for stable ABIs for C++ as it did for C, defining COM as a language-agnostic ABI for richer types and dynamic dispatch, with Visual Studio adding extensions to implement COM interfaces as if they were C++ types.

        The whole ‘C++ doesn’t have a stable ABI’ thing has not really been true for most of the history of standard C++. C++ was first standardised in 1998. The Itanium ABI was published, I believe, in 2000 (possibly earlier?). Every release of GCC since GCC 3.0 in 2001 has supported it. On *NIX platforms, we’ve had 26 years of standard C++ and 23 years of a stable C++ ABI. On Windows, COM predated standard C++ by five years and remains a stable ABI. Visual Studio occasionally changes its C++ ABI, because they regard COM, not the C++ ABI as their stable ABI, but that matters only on Windows.

        Note that the language having a stable ABI says nothing about libraries having a stable ABI. A lot of C and C++ libraries frequently break their public ABIs. C standard libraries typically haven’t since the introduction of ELF symbol versioning. C++ standard libraries try not to and use ABI tags and extra namespaces to try to avoid it. Libc++ has a bunch of things hidden behind ifdefs that would break ABIs (so you can use them when static linking or on platforms with weaker ABI guarantees). It also makes aggressive use of always-inline functions that forward to stable ones so that the unstable bits of the ABI can be hidden per compilation unit. C++ provides a fairly rich set of tools for people to maintain stable ABIs but that doesn’t guarantee that people will.

              I feel like the ultimate solution to FFI boundaries is to not have any FFI - just have interpreters for a bunch of languages in standard library and perform Futamara projections for function calls. Might be a bit heavy of a solution (you could even say it's battleship sized), but it allows you to eliminate risks with language models not lining up (e.g. if your base language is memory safe, your C functions are also memory safe), and it's easy to peek into internals of other languages code.

                bitwalker 2024-06-18 14:46:53

                I think the future of FFI is something along the lines of how the Wasm Component Model and its Canonical ABI is designed. There is some metadata associated with compiled objects that provide the description of the compiled "component" in terms of a common type system (i.e. what functions it exports, and the type signatures of those functions). Language-specific tooling can then generate the code that lifts to/lowers from the "canonical" ABI, allowing relatively seamless language interop for those languages which can speak that ABI.

                The Wasm Component Model takes things a step further, by dictating that components are shared-nothing, adding the notion of resources that have ownership semantics attached, as well as describing not just the components themselves, but how they are to be instantiated. That all requires some degree of runtime support. Despite that though, it really feels like a much more principled approach to FFI than anything else I've seen before. I guess it remains to be seen whether it works out, but I hope it does. The shared-nothing approach in particular really appeals to me because I think it would permit a greater degree of safe interop than is currently possible.

                Regardless, any FFI system inherently introduces friction, because you have to somehow deal with the inevitable impedance mismatch between the languages involved. Most languages just make the pragmatic choice to use the C ABI as a lowest common denominator to maximize the amount of existing code that can be integrated with, but it definitely feels like we can do better at this point.
